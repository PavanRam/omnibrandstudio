Overview & entrypoints

In Docker, two containers run the same image with different commands: the api container runs python -m uvicorn api.main:app and the worker container runs python -m worker.main. They share Postgres, Redis, the LiteLLM proxy, and Qdrant over the compose network.

Container boot (what exists before the request)

A

HTTP api container starts

backend/api/main.py → lifespan()
Uvicorn imports app = FastAPI(lifespan=lifespan). On startup the lifespan runs setup_observability("omnibrand-api") (OTEL; a no-op in local-dev), instrument_fastapi(app), then init_db() (asyncpg pool) and init_redis(). Routers are mounted: health, auth, campaigns, orgs, knowledge, plus evaluation only when should_enable_local_eval() is true (ENABLE_LOCAL_EVAL set & APP_ENV != production).
B

Ext worker container starts

backend/worker/main.py → __main__ → main()
Sets the Windows/psycopg event-loop policy, calls setup_observability("omnibrand-worker"), starts a Prometheus metrics server, then asyncio.run(main()) which does init_db() + init_redis() and enters an infinite redis.blpop("campaigns:queue", timeout=5) loop, waiting for work.

Flow A — POST /eval/local-eval (synchronous)

The whole pipeline runs inside the single HTTP request, in the api container. This is the path your Postman call exercises.

1

HTTP Request enters the ASGI middleware stack

api/main.py (metrics) · api/middleware/request_id.py · CORS
Three middlewares wrap every request. RequestIDMiddleware.__call__ reads/creates an X-Request-ID, stores it at request.state.request_id, and binds it into structlog context-vars (so every subsequent log line carries request_id=). The inline _record_http_metrics middleware times the request and increments Prometheus counters. CORS adds headers.
2

Router FastAPI validates the body and calls the handler

api/routers/evaluation.py → local_eval(body: CreateCampaignRequest, request)
FastAPI parses the JSON into CreateCampaignRequest (Pydantic) — a bad body returns 422 before your code runs. The handler reads request.state.request_id and mints campaign_id = new_campaign_id() (UUIDv7, core/ids.py).
3

Core Build the shared state object

pipeline/initial_state.py → build_initial_state(...)
Produces an OmniBrandState TypedDict (pipeline/state.py): the brief becomes a CampaignBrief, every accumulator list (variants, brand_scores, review_requests…) starts empty, current_phase="starting". This dict is the single contract passed to — and mutated by — every node.
4

Graph Build & invoke the graph

pipeline/graph.py → build_graph(...) → graph.ainvoke(state, config)
local_eval branches on settings.LOCAL_DEV_MODE. In Docker it's unset, so it takes the else branch: open an AsyncPostgresSaver checkpointer, call checkpointer.setup(), then build_graph(checkpointer, interrupt_before_review_gate=False). Note the review interrupt is off here, so local-eval never pauses. await graph.ainvoke(state, {"configurable": {"thread_id": campaign_id}}) runs the pipeline (see The LangGraph pipeline).
5

Router Shape and return the response

api/routers/evaluation.py (end of local_eval)
On success it logs local_eval_completed and returns {campaign_id, status:"completed", elapsed_ms, final_state} — the entire terminal OmniBrandState. Any exception is caught and re-raised as an HTTP 500 with the error. The response travels back out through the middleware, which appends the X-Request-ID header.

Flow B — POST /campaigns (asynchronous)

The api container only accepts and queues the work; the worker container runs the graph. This is the production-like path, and the one where human review can pause the pipeline.

1

Router Persist the campaign, then enqueue

api/routers/campaigns.py → create_campaign(body, request)
After the same middleware, this handler: normalizes org_id/brand_id (UUID, else 422); SELECTs the brands row (404 if missing, 403 if it belongs to another org); INSERTs a campaigns row with status='queued'; injects the OpenTelemetry trace context into the task; and redis.lpush("campaigns:queue", task). It returns 202 Accepted with a poll_url — the graph has not run yet.
2

Ext Worker pops the task

worker/main.py → main() loop → redis.blpop(...)
The worker's blocking loop returns the JSON payload and calls process_campaign(task). If that raises, the task is pushed to the campaigns:dead_letter list and a DLQ metric increments.
3

Ext process_campaign: rebuild state & mark running

worker/main.py → process_campaign(task_payload)
Re-validates the brief into CreateCampaignRequest, calls build_initial_state(...) (same object as Flow A), re-attaches the OTEL trace context, and UPDATE campaigns SET status='running' so the poll endpoint reflects progress.
4

Graph Run with the review interrupt ON

worker/main.py → AsyncPostgresSaver + build_graph(checkpointer)
Opens the Postgres checkpointer and calls build_graph(checkpointer) — here interrupt_before_review_gate defaults to True, so interrupt_before=["review_gate"] is compiled in. await graph.ainvoke(initial_state, config) runs the pipeline and, if it reaches the review gate, pauses and returns the checkpointed state — which survives a worker restart because it lives in Postgres.
5

Ext Decide the campaign's final status

worker/main.py (after ainvoke)
From the returned state: current_phase=="published" → published (done); any errors / budget-fail / invalid-brief → failed; otherwise the run paused → awaiting_review. It writes that status back to the campaigns row. Clients learn the outcome via GET /campaigns/{id}/status and GET /campaigns/{id} (which also reconstructs an in-memory trace from the checkpointer history).
Where they converge: both flows call the identical build_initial_state() → build_graph() → graph.ainvoke(). Everything below the graph is shared; only who runs it (api vs. worker) and whether the review interrupt is armed differ.

In Flow B the graph pauses before review_gate (interrupt). In Flow A that interrupt is off, so review_gate runs straight through.
Two invariants that explain the mechanics:
• The accumulator fields (variants, brand_scores…) are Annotated[list, operator.add], so the three parallel judges append instead of overwriting each other.
• Every node body is wrapped by safe_agent_run(), so a node that throws returns an errors entry instead of crashing the whole graph.

Core utilities every node leans on

i

Core safe_agent_run — the crash barrier

agents/base.py → safe_agent_run(agent_fn, state, task_id=None)
Each node is written as return await safe_agent_run(_impl, state). It runs the inner _impl, returns its partial-state dict on success, and on any exception logs agent_failed and returns {"errors": […]}. LangGraph merges that in and keeps going — which is why a failing agent degrades the run instead of aborting it.
ii

Core traced_llm_call — the single LLM chokepoint

agents/base.py → traced_llm_call(model, messages, task, state)
Every model call goes through here. It opens a Langfuse trace + OTEL span, then httpx.post(settings.LITELLM_BASE_URL + "/chat/completions", ...) — in Docker that URL is http://litellm:4000. On an HTTP error it logs llm_call_http_failed_using_fallback and substitutes deterministic fallback content instead of raising. It records Prometheus token/cost/latency metrics and best-effort writes a campaign_cost_attribution row (wrapped in try/except so a bookkeeping failure never fails the agent). Returns (content, usage).
Model aliases, not model names. Nodes pass an alias such as gen-free; the LiteLLM proxy maps it (via infra/litellm/litellm_config.yaml) to a concrete model — currently groq/llama-3.3-70b-versatile. That indirection is why a decommissioned model is a one-line config fix, not a code change.

Technology stack & what each does

Everything the project is built, tested, and run with — grouped by role, with the concrete job each piece does in OmniBrand. Sources: pyproject.toml, docker-compose.yml, frontend/package.json.

LiteLLM — the model gateway. Every traced_llm_call POSTs to the LiteLLM proxy (litellm:4000) rather than a provider directly. It maps aliases (gen-free, judge-1, util-fast…) to concrete models (infra/litellm/litellm_config.yaml), applies fallback chains + retry policy, caches responses in Redis, and enforces a spend budget. That indirection is why agent code never names a provider and a model swap is a one-line config change.
Langfuse — LLM observability. traced_llm_call opens a Langfuse trace per model call, recording the prompt, resolved model, output, token counts and cost, grouped under the campaign_id as a session. It's how you inspect what each agent actually sent and received. It degrades gracefully (logs langfuse_disabled_missing_keys) when keys aren't configured.
