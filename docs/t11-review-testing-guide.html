T11 — Review Gate & Human Review: Run & Test Guide

A step-by-step, copy-pasteable guide to exercise the human-in-the-loop review flow end-to-end with the full Docker stack and Postman. Steps mirror a verified run.

Overview

The review gate only triggers on the worker path (POST /campaigns): the worker runs the pipeline, the graph pauses before review_gate (interrupt_before), the review batch is persisted, and the campaign goes to awaiting_review. A reviewer then lists pending reviews and submits a decision, which resumes the graph.

Not /eval/local-eval. That endpoint runs the graph inline with the interrupt disabled and never persists a campaign row — so it will not pause for review and GET /campaigns/{id}/status would 404. Use POST /campaigns for review testing.

Prerequisites

  • Docker Desktop running.
  • A valid GROQ_API_KEY in the repo-root .env — content must actually generate (the free-tier gen-free model), otherwise no variant is reviewable and the campaign won't pause.
  • On a branch with the T11 review-gate code + its supporting fixes (asyncpg API-key auth, the groq/llama-3.3 model alias).
  • Do not set LOCAL_DEV_MODE — Docker uses the real services.

The review lifecycle

POST /campaigns api → Redis queue
→
worker runs graph intake → gen → judges → aggregator
→
INTERRUPT before review_gate
→
persist review_requests status = awaiting_review
→
GET /reviews reviewer sees pending
→
POST /reviews/{id}/decide
→
resume graph aupdate_state + ainvoke
→
approved / edited → published
|
rejected → regenerate → re-pause

1 · Bring up the stack & create the schema

1a

Start all services + build

docker compose up -d --build
Wait until docker compose ps shows postgres, redis, litellm healthy and api / worker up. (The api + worker containers run python -m uvicorn / python -m worker.main internally.)
1b

Apply migrations

docker compose exec api python -m alembic upgrade head

2 · Seed an org, brand & API key

The /reviews endpoints require auth, and POST /campaigns needs a brand under the default org (…0001). Run once (PowerShell, from repo root):

@'
INSERT INTO orgs (id, name, slug)
VALUES ('00000000-0000-0000-0000-000000000001','Demo Org','demo-org') ON CONFLICT (id) DO NOTHING;

INSERT INTO brands (id, org_id, name)
VALUES ('00000000-0000-0000-0000-000000000002','00000000-0000-0000-0000-000000000001','Demo Brand') ON CONFLICT (id) DO NOTHING;

INSERT INTO api_keys (org_id, brand_id, name, key_hash, key_prefix, scopes)
VALUES ('00000000-0000-0000-0000-000000000001','00000000-0000-0000-0000-000000000002','demo-key',
        encode(digest('omnibrand-demo-key','sha256'),'hex'),'omnibrand',
        ARRAY['campaigns:read','campaigns:write','reviews:read','reviews:decide']) ON CONFLICT (key_hash) DO NOTHING;
'@ | docker compose exec -T postgres psql -U omnibrand -d omnibrand
Reviewer API key = omnibrand-demo-key (its SHA-256 is what's stored; the app hashes the incoming X-API-Key and matches).

3 · Postman setup

In your Postman collection → Variables, add:

VariableValue
base_urlhttp://localhost:8000

Request 1 · Create a campaign

POST{{base_url}}/campaigns

Auth: none (server uses the default org). Headers: Content-Type: application/json. Body → raw → JSON:

{
  "brand_id": "00000000-0000-0000-0000-000000000002",
  "objective": "Launch our new API",
  "target_audience": "Developers",
  "key_messages": ["Fast", "Reliable"],
  "channels": ["email"],
  "locales": ["en-US"],
  "audience_segments": ["core"],
  "token_budget": 2000,
  "raw_text": ""
}

Expected 202:

{ "campaign_id": "019f…", "status": "queued", "poll_url": "/campaigns/019f…/status" }
Keep it single channel/locale/segment → exactly one review to decide. Copy campaign_id into the Postman variable.

Request 2 · Poll until it pauses

GET{{base_url}}/campaigns/{{campaign_id}}/status

Auth: none. Send every few seconds until status becomes awaiting_review (~10–45s while Groq generates + personalizes):

{ "campaign_id":"019f…", "status":"awaiting_review", "started_at":"…", "created_at":"…" }

Watch it live: docker compose logs -f worker → look for review_batch_persisted.

Request 3 · List pending reviews

GET{{base_url}}/reviews

Auth (required): header X-API-Key: {{api_key}}. Optional query: ?status=pending&limit=20&offset=0.

Expected 200:

{
  "reviews": [{
    "review_request_id": "11cf88d6-…",
    "variant_id": "…", "campaign_id": "019f…", "task_id": "en-US_email_core",
    "locale": "en-US", "channel": "email", "segment": "core",
    "status": "pending",
    "routing_reason": "flagged for human review",
    "sla_deadline": "…",
    "content": "Subject: …",
    "composite_score": 6.5,
    "scores_snapshot": [ {"judge_model":"claude", …}, {"judge_model":"gpt4o", …}, {"judge_model":"llama", …} ]
  }],
  "limit": 20, "offset": 0, "count": 1
}

Copy review_request_id into the Postman variable.

Request 4 · Submit a decision

POST{{base_url}}/reviews/{{review_request_id}}/decide

Auth (required): X-API-Key: {{api_key}}. Headers: Content-Type: application/json. Body → raw → JSON (the body is mandatory — an empty body returns 422 "Field required").

DecisionBody (raw JSON)Result
approve { "decision": "approved", "reviewer_note": "ship it" } publishes as-is
edit { "decision": "edited", "edited_content": "Subject: Final copy\n\n…", "reviewer_note": "tightened CTA" } publishes your edited_content as final_content
reject { "decision": "rejected", "reviewer_note": "too generic, redo" } regenerates & re-pauses (see status)
Validation rule: edited_content is required for edited and must be omitted for approved/rejected — otherwise you get a 422.

Expected 200 (last pending review for the campaign):

{ "review_request_id":"…", "decision":"approved", "status":"resumed", "campaign_status":"published" }

Expected 202 (other reviews still pending for the campaign):

{ "review_request_id":"…", "decision":"approved", "status":"recorded",
  "campaign_status":"awaiting_review", "detail":"awaiting remaining reviews for this campaign" }

Request 5 · Verify the outcome

GET{{base_url}}/campaigns/{{campaign_id}}

Auth: none. For approve/edit expect:

{
  "id": "019f…", "status": "published",
  "variants": [ { "task_id":"en-US_email_core", "status":"approved",
                  "final_content":"Subject: …", "composite_score":6.5 } ],
  "in_memory_trace": [ … ]
}

For an edit, final_content is your submitted text and status is edited.

DB & audit checks (optional)

docker compose exec -T postgres psql -U omnibrand -d omnibrand -c ^
  "SELECT status, decision, reviewed_at FROM review_requests WHERE campaign_id='<campaign_id>';"

docker compose exec -T postgres psql -U omnibrand -d omnibrand -c ^
  "SELECT action, entity_type FROM audit_log WHERE entity_type='review_request' ORDER BY created_at DESC LIMIT 3;"

Expect the review_requests row = approved with reviewed_at set, and an audit_log row with action = decide.

Airtable — setup & mirror (optional)

The Airtable mirror is optional, config-gated, and best-effort: Postgres review_requests is the source of truth; Airtable just mirrors pending + decided reviews for reviewer visibility. If it isn't configured it's a no-op and the pipeline is unaffected. Set it up only if you want reviews to appear in an Airtable grid.

Setup steps

A

Create an Airtable account & base

Sign up at airtable.com (free tier is fine) and create a base (Airtable's word for a database), e.g. "OmniBrand Reviews".
B

Create the table & its columns

Rename the default table to Reviews (must match AIRTABLE_TABLE). Add these fields — names must match exactly (case-sensitive) or Airtable returns 422 Unknown field name:
FieldType
review_request_idSingle line text
campaign_idSingle line text
variant_idSingle line text
statusSingle line text (or Single select: pending / approved / rejected / edited)
routing_reasonLong text
decisionSingle line text (or Single select: approved / rejected / edited)
The default primary field (e.g. "Name") can stay — the mirror never writes it. Don't enter the column names as data rows.
C

Get the Base ID

Open airtable.com/developers/web/api/introduction and pick your base — the Base ID starts with app…. (Also in the base URL: https://airtable.com/appXXXXXXXX/….)
D

Create a Personal Access Token (PAT)

At airtable.com/create/tokens create a token with scopes data.records:read + data.records:write and access to your base. Copy it — it starts with pat…. (Legacy API keys are deprecated; use a PAT.)
E

Add the three vars to .env (repo root)

AIRTABLE_API_KEY=patXXXXXXXXXXXXXX.XXXXXXXXXXXXXXXX
AIRTABLE_BASE_ID=appXXXXXXXXXXXXXX
AIRTABLE_TABLE=Reviews
All three must be non-empty for the mirror to activate (that's what airtable_enabled() checks). Do not commit .env — the token is a secret.
F

Reload the containers & verify

Env is read at container start, so recreate api + worker: 
docker compose up -d api worker
Then run a campaign (Reqs 1–4): a row is upserted on the pause (Req 2) and a decision row is appended on the decision (Req 4). The rows appear in your Reviews table.
Best-effort / non-fatal. If the token, Base ID, table name, or a column is wrong, the mirror logs a airtable_mirror_failed warning in docker compose logs api worker and the pipeline continues normally — Postgres stays the source of truth. The free tier allows 1,000 records per base.

Quick sanity check (from the repo root, reads .env, never prints the token):

uv run python - <<'PY'
import os, httpx
env = dict(l.strip().split("=",1) for l in open(".env") if "=" in l and not l.startswith("#"))
key, base, table = env.get("AIRTABLE_API_KEY",""), env.get("AIRTABLE_BASE_ID",""), env.get("AIRTABLE_TABLE","Reviews")
print("configured:", bool(key), bool(base), table)
if key and base:
    r = httpx.get(f"https://api.airtable.com/v0/{base}/{table}",
                  headers={"Authorization": f"Bearer {key}"}, params={"maxRecords":5}, timeout=15)
    print("HTTP", r.status_code, "records:", len(r.json().get("records", [])) if r.status_code==200 else r.text[:200])
PY

Gotchas

SymptomCause / fix
401 on /reviewsMissing/typo'd X-API-Key, or the seed (step 2) didn't run.
422 "Field required" on decideEmpty body — set Body → raw → JSON with the decision (see Req 4).
422 on decide (edited_content)You sent edited_content with approve/reject, or omitted it with edit.
Campaign never reaches awaiting_reviewContent generation failed (bad/empty Groq key → fallback content fails email constraints → no reviewable variant). Check docker compose logs worker for llm_call_http_failed_using_fallback.
404 brand not found on /campaignsSeed didn't run / brand not under org …0001.
409 on decideThe review_request_id was already decided — grab a fresh pending one from Req 3.
connection refusedDocker Desktop / the stack isn't running.

What's verified vs. partial

PathStatusNotes
Approveverified E2EDocker + Postman → published; DB rows + audit confirmed.
Editverified pathSame apply→resume→publish machinery; publishes your edited text.
Rejectpartial Regenerates & re-pauses (graph loop unit-tested, capped by MAX_REVIEW_ROUNDS=2), and the campaign returns to awaiting_review. Known gap: the API-driven 2nd round isn't actionable yet — the regenerated review isn't persisted on re-pause, so GET /reviews won't list it. Full design to complete it is in the design spec §16.1.

Endpoints: POST /campaigns, GET /campaigns/{id}/status, GET /campaigns/{id}, GET /reviews, POST /reviews/{id}/decide. Design reference: docs/superpowers/specs/2026-07-19-t11-review-gate-design.md.
